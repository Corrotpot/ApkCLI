# Запуск программ на Android без root

[English](../ANDROID_EXEC_NOTES.md) · **Русский**

Это ограничение, вокруг которого выстроен весь проект. Прочитайте этот текст,
прежде чем что-либо менять в том, как запускаются процессы.

## Правило

Начиная с **Android 10 (API 29)**, SELinux запрещает `execve()` для любого
файла в приватном каталоге данных приложения.

Механизм такой: файлы в `/data/data/<pkg>/` имеют тип SELinux `app_data_file`.
Домену `untrusted_app_29` и его преемникам — а именно в них работает
приложение с целевым API 29 или выше — не выдано разрешение
`app_data_file:file execute_no_trans`. Приложения с целевым API 28 или ниже
работают в `untrusted_app_27`, где это разрешение ещё есть.

Последствия, на которых теряется время, если о них не знать:

* `chmod +x` ничего не даёт. Это мандатное управление доступом, а не биты
  прав. По режиму файл исполняемый, но ядро всё равно отказывает.
* `execve` завершается с `EACCES`, а через `ProcessBuilder` это доходит в виде
  обычного `IOException`. О SELinux в сообщении ни слова.
  `ExecPolicy.explainRefusal` нужен, чтобы пользователь и модель узнавали, в чём
  на самом деле проблема, вместо того чтобы агент пробовал `chmod`, потом
  `sudo`, а потом сдавался.
* Это касается всего, что скачано, сгенерировано, распаковано или
  скомпилировано во время выполнения. Во время выполнения выйти из-под этого
  ограничения никак нельзя.

## Что можно запускать

### 1. `nativeLibraryDir`

`/data/app/~~<hash>/<pkg>-<hash>/lib/<arch>/`

Заполняется установщиком из `lib/<abi>/` внутри APK, имеет метку
`apk_data_file`, доступен только для чтения. Для непривилегированного
приложения это единственное место, куда можно записать при установке и откуда
можно запускать во время выполнения.

Две настройки сборки **обязательны** — это не оптимизации:

```kotlin
// app/build.gradle.kts и core/build.gradle.kts
packaging { jniLibs { useLegacyPackaging = true } }
```

```xml
<!-- AndroidManifest.xml -->
<application android:extractNativeLibs="true">
```

При современной упаковке установщик вообще не записывает библиотеки в файловую
систему — они отображаются в память прямо из (сжатого) APK, а файл, которого
нет на диске, нельзя запустить через exec. Стоит ошибиться в любой из этих
настроек — и всё окружение оболочки перестаёт работать, причём без ошибки,
которая указывала бы на причину.

Установщик распаковывает только файлы, подходящие под `*.so`, поэтому каждый
встроенный исполняемый файл поставляется как `lib<name>.so`:

```
jniLibs/arm64-v8a/libbusybox.so   ->  $PREFIX/bin/busybox
jniLibs/arm64-v8a/libgit.so       ->  $PREFIX/bin/git
```

**Этот путь меняется при каждом обновлении приложения.** В нём есть хеши,
привязанные к конкретной установке. Нигде нельзя кешировать его между
версиями; `Bootstrap` пересоздаёт всю ферму симлинков при каждой смене кода
версии или каталога, потому что иначе после обновления все ссылки в
`$PREFIX/bin` окажутся висячими.

### 2. `/system/bin` и `/system/xbin`

Доступны всегда, настраивать ничего не нужно:

* `sh` — mksh. POSIX, не bash. Нет `[[ ]]`, нет массивов, нет подстановки
  процессов.
* `toybox` — около 150 апплетов на современном устройстве: `ls`, `cat`,
  `grep`, `sed`, `find`, `tar`, `env`, `ps`, `kill` и так далее.
* `linker64`, `app_process`, `dumpsys`, `getprop` и им подобные.

Это нижняя планка. Даже если ничего не встроено, у приложения есть рабочая
оболочка.

### 3. Скрипты оболочки — всегда

Эту лазейку стоит усвоить: когда вы запускаете `sh script.sh`, через exec
запускается **интерпретатор**, а скрипт всего лишь *читается*. Читать файл из
собственного каталога данных приложения вполне разрешено.

Поэтому скрипты работают везде, в обоих флейворах, без ограничений. Затронуты
только скомпилированные бинарники.

## Что не работает

| Попытка | Почему нет |
| --- | --- |
| Скачать статический бинарник и запустить его | Попадает в каталог данных. Отказ. |
| Сделать бинарнику `chmod 777` | Не имеет значения. Дело не в правах доступа. |
| `/data/local/tmp` | Принадлежит пользователю `shell`. Приложение не может туда писать. |
| `proot` со скачанным rootfs | Сам proot может запускаться из APK, но гостевые бинарники, которые он запускает через `execve`, всё равно проходят через ядро, а ядро по-прежнему отказывает. proot перехватывает разрешение путей, а не SELinux. |
| `memfd_create` + `fexecve` | Анонимная исполняемая память для `untrusted_app` запрещена. |
| Скомпилировать на устройстве и запустить результат | Тот же отказ, да и компилятора, который смог бы запуститься, всё равно нет. |
| `sudo`, `su` | Root нет. Доступных setuid-бинарников нет. |
| `apt`, `apk`, `pkg`, `dnf`, `brew` | Системного менеджера пакетов нет, и устанавливать некуда. Во флейворе `power` их место занимает собственный `pkg_install` приложения; см. ниже. |

`ShExecTool` перехватывает `sudo`, `apt`, `systemctl` и им подобные *до*
запуска процесса и возвращает объяснение. Без этого модель видит «not found»,
пробует вариацию и впустую тратит три хода.

## Почему флейворов два

```
play   targetSdk 36   untrusted_app_3x   exec из каталога данных ЗАПРЕЩЁН   можно публиковать
power  targetSdk 28   untrusted_app_27   exec из каталога данных РАЗРЕШЁН   ставить только вручную (sideload)
```

Флейвор `power` — не хак: Termux годами держался именно на этом. И Android 15,
и Android 16 отказываются устанавливать только приложения с `targetSdk < 24`,
поэтому APK с целевым API 28 в 2026 году по-прежнему устанавливается. Его
просто нельзя выложить в Play.

`ExecPolicy` определяет уровень по `applicationInfo.targetSdkVersion`, а не по
флагу `BuildConfig`, поэтому не ошибётся, даже если флейвор, манифест и файлы
Gradle когда-нибудь разойдутся.

### Эмпирическая проверка

Выводить политику из целевого SDK в теории правильно, но производители
поставляют изменённые политики SELinux, а такой сбой — когда каждый вызов
инструмента возвращает `EACCES` — мучительно диагностировать по баг-репорту.
Поэтому `ExecPolicy.probe()` при запуске действительно выполняет
`sh -c "echo apkcli-ok"` и записывает результат в штамп бутстрапа.

## Проблема шебанга

В Android нет ни `/bin`, ни `/usr/bin`, ни `/etc`, ни `/tmp`, ни `/home`.

Это ломает значительную часть реальных скриптов, а строку `#!` ядро
обрабатывает *раньше*, чем успеет вмешаться какой-либо код в пространстве
пользователя: `execve("script.sh")` заставляет ядро прочитать `#!/bin/sh` и
искать `/bin/sh`, которого не существует. `ENOENT` — и перехватывать нечего.

`native/execshim` решает это так же, как `termux-exec`, — библиотекой для
`LD_PRELOAD`, которая перехватывает `execve`, `execv`, `execvp` и `execvpe`:

1. Абсолютные пути в стиле Linux (`/bin/sh`, `/usr/bin/env`) переписываются на
   `$PREFIX/bin/<name>`, затем на `nativeLibraryDir/lib<name>.so`, затем на
   `/system/bin/<name>`.
2. Шебанг до системного вызова читаем **мы сами**, интерпретатор разрешается
   через то же переписывание путей, и через exec запускается интерпретатор со
   скриптом в качестве аргумента.

3. Собственный префикс Termux, `/data/data/com.termux/files/usr/...`,
   отображается на `$APKCLI_PREFIX/...`, если исходного пути нет, — для
   установленных пакетов, чьи бинарники не удалось перенести (см. ниже).

Настраивается через окружение, чтобы обойтись без вкомпилированных путей:
`APKCLI_PREFIX`, `APKCLI_NATIVE_BIN`. Если хотя бы одна из них не задана, шим
пропускает каждый вызов без изменений, так что неправильно настроенное
окружение деградирует до обычного поведения Android, а не ломает exec целиком.

## Установка пакетов Termux (power)

Termux собирает каждый пакет под `/data/data/com.termux/files/usr`, и эта
строка повсюду: в шебангах, в `DT_RUNPATH` каждого ELF-файла, в каталоге
сертификатов OpenSSL, в оболочке для `subprocess` в Python, в каталоге
семафоров `libandroid-posix-semaphore`. `PackageManager` переписывает её при
распаковке.

**Псевдоним той же длины.** `/data/data/com.termux/files/usr` — 31 символ, и
`/data/data/dev.apkcli.power/usr` — тоже. `/data/data/<package>` — это
собственный каталог данных приложения, поэтому симлинк `usr -> files/usr` в
нём выводит этот путь на настоящий `$PREFIX`. Замену той же длины можно
применить к *каждому* файлу, включая бинарники, не сдвинув ни одного
смещения, — и тогда пакет ведёт себя в точности как в Termux. Псевдоним
проверяется по inode, а не по каноническому пути: при изоляции данных
приложений (Android 11+) `/data/data/<pkg>` и `/data/user/0/<pkg>` — это
отдельные монтирования одного каталога, и их канонические пути никогда не
совпадают.

**Без псевдонима** (более длинное имя пакета, как у отладочной сборки, или
дополнительный пользователь) текстовые файлы получают настоящий путь, в
ELF-файлах runpath переписывается на месте на `$ORIGIN/../lib` и т. п. —
bionic раскрывает `$ORIGIN` начиная с API 24, а относительная форма всегда
короче, — а пути, вкомпилированные в бинарники, остаются как есть.
`ExecPolicy` покрывает те из них, у которых есть переопределение
(`SSL_CERT_FILE`, `TERMINFO`, `GIT_EXEC_PATH`, переменные CA для curl/git).

У `$PREFIX/tmp` переопределения нет, и он важнее, чем кажется: он вкомпилирован
в `libandroid-posix-semaphore` (`.../usr/tmp/sem.*`) и `libandroid-shmem`
(`.../usr/tmp/ashv_key_*`) из Termux, а в PostgreSQL — как каталог сокетов.
В Android нет SysV IPC; эти две библиотеки его эмулируют (разделяемая память
поверх ashmem, семафоры — файлами в `$PREFIX/tmp`), и только благодаря им
Termux вообще может запускать PostgreSQL. Если путь недоступен, PostgreSQL
принимает сбой за коллизию имён и пробует следующее имя — до бесконечности:
`initdb` зацикливается на «selecting default max_connections». Поэтому в этом
режиме более длинные пути внутри префикса всё же получают псевдонимы той же
длины там, где они помещаются: `$PREFIX/tmp` — 35 символов, и
`/data/data/dev.apkcli.power.debug/t` — тоже (или `/data/user/10/<pkg>/tmp_`
для дополнительного пользователя); так же обрабатываются `bin`, `etc`, `lib`,
`libexec`, `share`, `include` и `var` — `bin` потому, что `pg_ctl` запускает
сервер через `execl(".../usr/bin/sh")`, и когда псевдоним был только у `tmp`,
это падало с ENOENT. В бинарники они вписываются только там, где путь Termux
является целым компонентом пути (за ним идёт `/` или NUL). В текстовых файлах
остаётся прямой путь. Ссылка, которая уже есть в каталоге данных и указывает
не внутрь `files/`, никогда не трогается.

**`LD_LIBRARY_PATH` не должен содержать `$PREFIX/lib`.** Bionic просматривает
`LD_LIBRARY_PATH` раньше `DT_RUNPATH`, причём для любого процесса, включая
`/system/bin`: toybox загрузил бы `libcrypto.so` из OpenSSL 3 от Termux вместо
системного BoringSSL. Пакеты находят свои библиотеки через собственный runpath,
как и в Termux.

Оболочкой инструмента остаётся `sh` из фермы (системный mksh): `bash` или
`dash` из пакета в `$PREFIX/bin` не подхватывается как оболочка агента, поэтому
его обновление или удаление не утянет за собой инструмент оболочки.

## PTY всё-таки работают

Об этом стоит сказать, потому что это неожиданно: `/dev/ptmx` доступен из
песочницы недоверенного приложения. Для настоящей пары master/slave root не
нужен.

`native/apkcli-core/src/pty.rs` открывает его вручную, а не через `openpty` из
bionic, доступность которого по уровням API в разных версиях NDK неодинакова:

1. `open("/dev/ptmx", O_RDWR | O_CLOEXEC)`
2. `ioctl(TIOCSPTLCK, &0)` — разблокировка
3. `ioctl(TIOCGPTN, &n)` — slave-сторона: `/dev/pts/<n>`
4. `fork`, затем в дочернем процессе: `setsid`, `ioctl(TIOCSCTTY)`, `dup2` на
   0/1/2, сброс диспозиций сигналов, `execve`

Номера ioctl одинаковы на всех Linux ABI, под которые здесь идёт сборка.

Между `fork()` и `execve()` дочерний процесс может вызывать только
async-signal-safe функции. Поэтому все выделения памяти — argv, envp,
разрешённый путь — происходят *до* форка. Это самый рискованный код в проекте;
почему со временем он должен жить в отдельном процессе, см. раздел
«Изоляция процессов» в `ARCHITECTURE.md`.

## Встраивание бинарника, который действительно запускается

В порядке должны быть три вещи, и каждая ломается по-своему:

**Слинкован с bionic, а не с glibc.** Бинарник, собранный на настольном Linux,
запрашивает в качестве ELF-интерпретатора `/lib/ld-linux-aarch64.so.1`.
Бинарники Android запрашивают `/system/bin/linker64`. Поэтому
`tools/fetch-prebuilts.ps1` скачивает пакеты Termux, а не собирает их из
исходников на десктопе.

```sh
readelf -l libgit.so | grep interpreter   # => /system/bin/linker64
```

**Никаких остатков `DT_RUNPATH`.** В бинарниках Termux зашит runpath
`/data/data/com.termux/files/usr/lib`, которого нет на устройстве без Termux, а
линкер пробует его первым.

**Не** используйте `patchelf --remove-rpath`: он перестраивает таблицу
программных заголовков и может изменить число и порядок сегментов `PT_LOAD`, а
Android 11+ такое отвергает. Вместо этого `tools/zero-runpath.py` на месте
обнуляет `d_val` у записей `DT_RPATH`/`DT_RUNPATH` — так они указывают на
обязательную пустую строку с индексом 0 в `.dynstr`. Ничего не сдвигается, все
смещения остаются корректными.

```sh
readelf -d libgit.so | grep -E 'RPATH|RUNPATH'   # => ничего или пусто
```

**Выравнивание по страницам 16 КБ.** Устройства с Android 15+ могут
использовать базовые страницы по 16 КБ, а с 1 февраля 2027 года Play
отклоняет обновления, нативные библиотеки которых не выровнены. В NDK r28 для
C/C++ это берёт на себя драйвер clang, но Rust вызывает линкер сам, поэтому
`native/.cargo/config.toml` передаёт флаги явно:

```
-C link-arg=-Wl,-z,max-page-size=16384
-C link-arg=-Wl,-z,common-page-size=16384
```

`common-page-size` сохраняет совместимость результата с устройствами со
страницами 4 КБ.

```sh
readelf -lW libapkcli_core.so | grep LOAD   # => Align 0x4000
```
